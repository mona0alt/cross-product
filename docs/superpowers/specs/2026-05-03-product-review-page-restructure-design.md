# 商品审核页重构设计文档

## 1. 背景

当前后台商品审核页由多个功能块直接平铺在同一屏中，包括：

- 手动新增商品
- 自动抓取源监控
- 待审核商品列表
- 多语言内容翻译与审核面板

虽然这些模块都与商品中心相关，但它们目前同时出现在一个工作区里，页面缺少明确的任务层级与阅读顺序，导致用户进入页面后很难快速理解：

- 当前主任务是什么
- 先看哪里
- 再做什么
- 最终在哪里完成审核决策

用户已经明确指出当前页面“都是平铺在页面的，有点没有逻辑”，并在后续确认中进一步明确了本次重构的目标与边界。

## 2. 已确认约束

本轮设计已经和用户确认以下前提：

- 优先解决“审核流程更清晰”，而不是只做样式美化
- `手动新增商品` 需要保留在当前页面中
- 页面内允许使用 `Tab` 或其他方式对任务进行分组
- 主交互模式采用 `列表 + 详情侧栏`
- 本轮需要先给出可视化 UI 预览，再进入实现

这意味着本次不是把“手动新增商品”直接拆到新路由，而是要在同一路由中建立更清晰的信息架构。

## 3. 设计目标

本次重构的核心目标是把当前商品页从“平铺式工作台”重构为“分任务的审核页”。

成功标准如下：

- 用户进入页面后，能一眼区分 `商品审核` 和 `手动新增` 是两种不同任务
- 默认进入 `商品审核` 视图，建立清晰的审核主流程
- 审核视图内部形成 `队列 -> 详情 -> 审核动作` 的稳定顺序
- 手动新增保留在当前页面，但不再和审核流程同屏抢焦点
- 现有 mock 数据与后台演示能力继续可用，不扩大真实业务边界

## 4. 方案对比与结论

本轮评估过以下三种方案：

### 4.1 方案 A：顶部 Tab 切任务

在商品页顶部增加两个主 Tab：

- `商品审核`
- `手动新增`

默认进入 `商品审核`。用户在同一路由下切换任务，但同一时刻只专注于一个任务场景。

优点：

- 同时满足“保留在当前页面”和“不要继续平铺”的要求
- 审核和新增两种心智模型彻底分开
- 最适合当前代码结构演进，不需要改路由

### 4.2 方案 B：左侧任务导航

把当前页再做一层次级导航，用侧边菜单切换：

- 待审核商品
- 手动新增
- 抓取监控

优点是层次明确，但会让当前页面像“后台套后台”，结构偏重，不适合本页体量。

### 4.3 方案 C：同页折叠分组

保留当前大致结构，只把 `手动新增商品` 变成可展开折叠区，默认收起。

改造成本最低，但本质上仍然是“同页堆叠”，逻辑改善有限。

### 4.4 最终结论

本次采用 `方案 A：顶部 Tab 切任务`。

原因：

- 任务边界最清楚
- 不改变当前路由结构
- 最符合用户对“页面保留但更有逻辑”的目标
- 可以自然承接 `列表 + 详情侧栏` 的审核工作流

## 5. 页面整体结构

商品页重构后分为三个层次：

### 5.1 页级标题区

保留统一后台页头，承载：

- `商品审核` 标题
- 页面说明
- 抓取日志入口
- 状态摘要或导出入口

页头只承担模块说明和高层入口职责，不再混入具体审核表单。

### 5.2 主任务 Tab

页头下新增主 Tab：

- `商品审核`
- `手动新增`

规则如下：

- 默认激活 `商品审核`
- 当前激活态必须足够明显
- 切换时只替换主内容区，不更改页头

### 5.3 主内容区

不同 Tab 显示不同任务视图：

- `商品审核`：列表驱动的审核工作流
- `手动新增`：录入驱动的表单工作流

这样页面虽然仍是同一个地址，但任务边界被清晰切开。

## 6. 商品审核 Tab 设计

`商品审核` 是默认视图，也是本页的核心主任务。

### 6.1 布局结构

桌面端采用双栏结构：

- 左栏：待审核队列
- 右栏：当前审核详情

推荐比例为：

- 左侧约 `5`
- 右侧约 `7`

目标是让左侧负责“找条目”，右侧负责“做判断”。

### 6.2 左栏：待审核队列

左栏负责建立审核入口，包含三层内容：

#### 第一层：筛选与搜索

包含：

- 搜索框
- 来源筛选
- 状态筛选

这部分只保留审核最需要的控件，不再夹杂新增表单或大块说明内容。

#### 第二层：审核摘要

以轻量摘要卡展示：

- 待审核数量
- 待补充信息数量
- 可发布数量

摘要只用于快速建立工作量感知，不抢主列表焦点。

#### 第三层：商品队列

每个商品条目展示最关键的审核信息：

- 商品标题
- SKU
- 分类
- 来源
- 完整度
- 当前状态
- 简短审核建议

交互规则：

- 默认选中第一条待审核商品
- 选中态要明显
- 点击任意条目时，右侧详情立即联动更新

### 6.3 右栏：当前审核详情

右栏作为唯一决策区，聚合当前商品的全部审核信息。

内部按阅读顺序分为四块：

#### 基础信息

展示：

- 商品标题
- 分类
- SKU
- 来源
- 价格
- 库存或补充交易信息

#### 内容校验

展示当前审核所关心的字段完成情况，例如：

- 标题是否完整
- 图片数量是否足够
- 英文摘要是否缺失
- 重复风险是否异常

#### 审核建议

以一块较高视觉权重的说明区承载系统建议，例如：

- 是否建议直接上架
- 哪些字段还需补充
- 当前风险点在哪里

#### 审核动作

操作区固定在详情区域底部，集中放置：

- `拒绝此条目`
- `退回补充`
- `审核通过并上架`

目标是让用户切换商品时始终知道最终动作在哪里执行。

### 6.4 自动抓取源监控的处理方式

当前页面中的 `自动抓取源监控` 不再保留为一个大模块卡片。

调整为以下之一：

- 页头摘要中的轻量状态信息
- 审核 Tab 顶部的一行小型状态卡

它的职责是提供背景状态，不再占据与审核队列同等级的大块空间。

## 7. 手动新增 Tab 设计

`手动新增` 仍然保留在当前页中，但切换后进入独立任务视图。

### 7.1 设计原则

手动新增与商品审核不是同一种操作心智：

- 审核是判断任务
- 新增是录入任务

因此必须通过 Tab 分开，而不是继续同屏并列。

### 7.2 结构划分

`手动新增` Tab 分为上下两段：

- 上方：录入表单
- 下方或右侧：提交前检查

桌面端推荐采用：

- 左侧主表单
- 右侧检查面板

### 7.3 录入表单分组

表单按填写顺序组织为三组：

#### 基础信息

- 商品标题
- 分类
- SKU
- 来源类型

#### 交易信息

- 价格
- 库存
- 币种
- 上架语言

#### 媒体与描述

- 图片上传
- 商品描述
- 多语言内容

### 7.4 提交前检查

通过轻量检查卡告诉用户当前录入结果是否适合提交，包括：

- 基础信息是否完整
- 图片是否达标
- 多语言字段是否缺失
- 提交后会进入什么状态

这块内容用于替代当前页面里混杂在表单中的弱提示。

### 7.5 操作区

底部操作区只保留两个主动作：

- `保存草稿`
- `保存到待审核`

提交成功后需要给出清晰反馈，例如：

- 已进入待审核队列
- 可一键切回 `商品审核` 继续处理

## 8. 响应式策略

桌面端以双栏布局为主。

移动端和窄屏场景下，布局按以下原则降级：

- `商品审核` 从双栏改为上下结构
- 先展示待审核队列，再展示当前详情
- 审核动作仍保持在详情区域底部
- `手动新增` 从左右结构改为上下堆叠

目标是保持任务顺序不变，只调整版式。

## 9. 组件拆分方案

当前 `ProductCenter` 组件承担了整页多个职责，重构后需要拆分为更清晰的结构。

### 9.1 页面编排层

保留 `ProductCenter` 作为页面编排组件，负责：

- 主 Tab 状态
- 当前选中商品状态
- 页面级摘要数据
- 子模块组合

### 9.2 商品审核相关组件

建议新增或拆分为：

- `ProductAuditTab`
- `ProductAuditQueue`
- `ProductAuditDetail`
- `ProductAuditActions`

职责如下：

- `ProductAuditTab`：组合审核视图
- `ProductAuditQueue`：展示队列、筛选和选中态
- `ProductAuditDetail`：展示当前商品详情与校验信息
- `ProductAuditActions`：承载审核动作按钮

### 9.3 手动新增相关组件

建议新增或拆分为：

- `ProductCreateTab`
- `ProductCreateForm`
- `ProductCreateChecklist`

职责如下：

- `ProductCreateTab`：组合新增视图
- `ProductCreateForm`：负责表单字段展示
- `ProductCreateChecklist`：负责提交前检查与提示

### 9.4 现有组件调整

当前 `ProductReviewDrawer` 已不再符合新角色命名，建议重构并重命名为：

- `ProductAuditDetail`

原因是重构后它不再是“抽屉”，而是右侧固定详情区域。

## 10. 数据与状态设计

本轮不要求扩展真实后端能力，但需要让展示层状态结构与新布局对应。

### 10.1 页面级状态

建议包含：

- `activeTab`
- `selectedProductId`
- `filters`
- `createFormDraft`

### 10.2 数据组织

当前 mock 数据里的 `review` 是单一对象，不足以支撑“点击不同商品，详情跟着变”的新交互。

建议把审核详情结构与每条商品数据建立关联，例如：

- 每个 row 可映射到一个 review detail
- 或新增独立详情映射对象，以 `id` 关联

### 10.3 默认行为

规则如下：

- 首次进入页面时默认激活 `商品审核`
- 默认选中第一条待审核商品
- 提交新增商品后，商品进入待审核队列

## 11. 测试策略

现有测试只验证静态标题是否出现，无法覆盖新的任务流。

### 11.1 需要补强的测试

建议增加以下三类测试：

#### Tab 切换

验证：

- 默认显示 `商品审核`
- 切换到 `手动新增` 后显示表单与检查区

#### 队列联动

验证：

- 点击不同商品条目
- 右侧详情随选中项变化

#### 新增提交流程

验证：

- 新增 Tab 提交后出现成功提示
- 可以引导回待审核视图

### 11.2 现有测试调整

`tests/unit/admin-product-center.test.tsx` 应从“静态标题断言”升级为围绕任务流的测试，而不是只检查页面上出现了几个区块标题。

## 12. 受影响文件

本轮重构预计主要影响以下文件：

- `src/app/admin/(protected)/products/page.tsx`
- `src/components/admin/product-center.tsx`
- `src/components/admin/product-review-drawer.tsx`
- `src/components/admin/admin-table-shell.tsx`
- `src/features/admin/mock-backoffice.ts`
- `tests/unit/admin-product-center.test.tsx`

如需新增组件，预计新增位置为：

- `src/components/admin/` 目录下的商品审核与手动新增子组件

## 13. 明确不做

本轮不涉及：

- 新增真实审核 API
- 扩展真实抓取监控能力
- 改造数据库结构
- 调整后台路由
- 在本轮内实现复杂拖拽上传或真实草稿持久化

本轮聚焦于：

- 页面结构重组
- 组件拆分
- 任务流程清晰化
- 演示层交互优化

## 14. 验收标准

当以下条件成立时，本轮设计视为达标：

- 商品页不再出现多个主任务模块平铺同屏
- 用户能够通过 Tab 清晰区分 `商品审核` 与 `手动新增`
- `商品审核` 内部形成稳定的 `队列 -> 详情 -> 动作` 流程
- `手动新增` 在当前页中保留，但不干扰审核主流程
- 页面结构与已确认的 UI 预览方向保持一致

## 15. 后续实现顺序建议

确认本设计后，建议按以下顺序进入实现：

1. 改造 `ProductCenter` 为 Tab 编排组件
2. 拆出审核视图与新增视图
3. 重构 `ProductReviewDrawer` 为固定详情组件
4. 调整 mock 数据结构以支撑详情联动
5. 更新单元测试，覆盖 Tab、联动和提交流程

这个顺序可以先建立页面框架，再补数据联动与测试，风险最小。
